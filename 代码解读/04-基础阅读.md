这一层回答一个问题：**PDF 里的文字怎么变成数据库里的记录？**

## 一、`reading.py`（160 行）—— 阅读的总指挥

### 1. 版本常量与页码解析

```python
PIPELINE_VERSION = 'pdfium-text-v2-ppocr5-cpu-v1'
```

基础阅读管线的历史编号：PDFium 提取 + PaddleOCR v5。字符串里的 `cpu` 不是运行设备；GPU 与 CPU 的 OCR 文本一致，所以换卡不改这个版本，已成功的页不会重跑。真正的版本号后面还要拼模型指纹（见下文）。

```python
def parse_pages(value, total):
    for item in value.split(','):
        if not re.fullmatch(r'\d+(?:-\d+)?', item.strip()):
            raise ValueError('页码格式须为 1-5,8；单批最多 20 页。')
        first, last = [int(x) for x in item.strip().split('-')][0], [...][-1]
        if first < 1 or last < first or last > total or last-first >= 20:
            raise ValueError('页码超出范围，或单批超过 20 页。')
        pages.update(range(first, last+1))
        if len(pages) > 20:
            raise ValueError('单批最多 20 页。')
    return sorted(pages)
```

把用户输入的 `'1-5,8'` 解析成 `[1,2,3,4,5,8]`。逐条防御：格式不对、范围越界、倒区间（5-1）、单段超 20 页、累计超 20 页，全部拒绝。**"单批 20 页"不是拍脑袋：CPU 上模型推理慢，批次太大一次调用要跑很久，暂停也反应不过来。**

### 2. `normalize_ocr()` —— 把 Paddle 的输出对齐

```python
for text, score, box in zip(payload.get('rec_texts',[]), payload.get('rec_scores',[]), payload.get('rec_polys',[]), strict=True):
```

PaddleOCR 返回三个**平行列表**：识别出的每行文字、每行置信分、每行四个角坐标。`zip(strict=True)` 强制三个列表长度一致——不一致就抛 `ReadingError`，**绝不允许"文字有、坐标缺"的残缺数据往下走**（后面按行定位裁剪区域全靠坐标）。分数还要检查是 0–1 的有限数。

### 3. `worker_records()` —— 全项目最重要的 25 行：worker 子进程协议

```python
def worker_records(python, worker, manifest, directory, timeout_seconds=1200):
    if not Path(python).is_file():
        raise ReadingError('工作进程 Python 未配置，请检查 DDA_PDF_PYTHON／DDA_OCR_PYTHON。')
    manifest_path = directory / (worker + '-' + uuid4().hex + '.json')
    manifest_path.write_text(json.dumps(manifest, ensure_ascii=False), encoding='utf-8')
```

第一步：把任务参数（模式、路径、页码列表……）打包成 JSON 清单写到磁盘。**为什么不直接命令行传参？** 参数里有路径、页码列表等复杂结构，走文件更稳，也方便事后排查（清单和日志都留在临时目录里）。

```python
env = {key: value for key, value in os.environ.items()
       if key.upper() in {'SYSTEMROOT','WINDIR','PATH','TEMP','TMP','USERPROFILE','LOCALAPPDATA','APPDATA','COMSPEC'}}
env.update(PYTHONUTF8='1', PYTHONIOENCODING='utf-8', HF_HUB_OFFLINE='1', ...)
```

第二步：**环境变量白名单**。子进程拿到的环境变量是"抄写"出来的——只带系统运行必需的那几个，**主进程环境里的数据库密码、各种密钥统统不带**。`HF_HUB_OFFLINE=1` 禁止 HuggingFace 联网（模型必须是本地已有的）。

```python
process = subprocess.Popen([str(python), str(script), str(manifest_path)],
                           stdout=subprocess.PIPE, stderr=log, text=True, encoding='utf-8', env=env)
timer = Timer(timeout_seconds, process.kill); timer.daemon = True; timer.start()
try:
    for line in process.stdout:
        yield json.loads(line)            # ← 生成器：逐行吐结果
    if process.wait() != 0:
        raise ReadingError('PDF／OCR 工作进程失败...')
finally:
    timer.cancel(); process.stdout.close()
    if process.poll() is None: process.kill()
    process.wait()
```

第三步是灵魂：
- `subprocess.Popen` 用指定 venv 的 python 启动 worker 脚本，stdout 接管道，stderr 进日志文件（Paddle 的调试输出不会污染结果流）。
- `Timer(timeout, process.kill)`：到点强杀的看门狗。
- **`yield` 让这个函数变成生成器**：worker 每输出一行 JSON，主进程就立刻拿到一个结果去处理（比如保存一页），不用等整个子进程跑完。这是"第 1 页处理完就能先入库"的关键。
- **`finally` 块是防内存泄漏的关键**：如果上层因为"暂停"提前不再取数（生成器被 close），Python 会在生成器里抛 GeneratorExit，finally 执行——取消定时器、**杀掉还没退出的子进程、等它真正结束**。否则会出现诡异局面：文件锁已经释放，但旧 worker 的模型还占着内存，下一次调用再加载一份新模型，内存直接翻倍。注释原文就写着这个场景。

### 4. `Reader.read()` —— 阅读主流程

**(a) 计算阅读版本**（第 113–125 行）：

```python
for name in ['PP-OCRv5_mobile_det','PP-OCRv5_server_rec','PP-LCNet_x1_0_doc_ori','PP-LCNet_x1_0_textline_ori']:
    for suffix in ['pdiparams','json','yml']:
        file = self.settings.ocr_models_dir / name / ('inference.' + suffix)
        digest.update((name+suffix).encode())
        if file.is_file():
            with file.open('rb') as stream:
                for block in iter(lambda: stream.read(1024*1024), b''):
                    digest.update(block)          # 权重文件逐字节参与指纹
        else:
            digest.update(b'missing')
version = PIPELINE_VERSION + '-' + digest.hexdigest()[:16] + f'-render{scale}' + ('-force-ocr' if force_ocr else '')
```

把 4 个 OCR 模型的 12 个文件**逐字节**喂进 SHA-256。意义：哪怕你只换了一个模型文件里的一个字节，指纹就变，阅读版本就变，旧版本的页面自动"退出版本"。这是全项目版本链的第一环。

**(b) 算待处理页**：

```python
existing = {p['page_number'] for p in self.database.pages(document_id) if p['status']=='succeeded'}
skipped = sorted(existing.intersection(pages))     # 当前版本已成功的 → 跳过
pending = sorted(set(pages) - existing)            # 其余 → 待处理
```

跳过只看**当前版本**的成功页——版本一换，同一页就要重读。

**(c) 两段式处理**：

```python
with closing(worker_records(pdf_python, 'pdf_worker', {...'mode':'read'...}, directory)) as records:
    for page in records:
        if page.get('error_code'): persist(page, 'text')       # 失败页也存失败记录
        elif force_ocr or page['route']=='ocr':
            ocr_pages.append(page)                              # 攒起来，稍后统一 OCR
        else: persist(page, 'text')                             # 文字页直接保存

if ocr_pages:
    with closing(worker_records(ocr_python, 'ocr_worker', {'pages': ocr_pages}, directory)) as records:
        for result in records:
            if 'payload' in result: result.update(normalize_ocr(result.pop('payload')))
            persist(result, 'ocr')
```

- `closing(...)` 包住生成器：即使中途抛异常也保证走 finally 清理子进程。
- **文字页和扫描页分两批**：pdf_worker 一趟处理完所有页（它很快），需要 OCR 的页攒成一个列表，交给 ocr_worker **一次调用处理整批**——OCR 进程启动慢、加载模型慢，攒批是为了摊薄这个成本。
- `persist()` 里先 `save_page` 提交数据库，再调 checkpoint——**又是"先落库再暂停"**。
- 最后的 `except ReadingError`：worker 中途崩了，已保存的页不动，只为没保存的页补失败记录——**失败的粒度是页，不是整批**。

## 二、`workers/pdf_worker.py`（75 行）—— PDFium 小工

跑在 `.venv-docling` 里（目录名是历史遗留，实际用的是 pypdfium2，不是 Docling）。**stdout 逐行输出 JSON**，就是上一节说的协议对端。

### 文字路由判定（这是它最核心的逻辑）

```python
def text_route(text):
    compact = re.sub(r'\s', '', text)
    if len(compact) < 16 or '\ufffd' in compact:
        return 'ocr'                       # 几乎没字，或全是乱码占位符
    unusual = re.sub(r'[\u4e00-\u9fffA-Za-z0-9，。；：、""''（））《》【】—–·％￥\x21-\x7e]', '', compact)
    if len(unusual)/len(compact) > 0.02:
        return 'ocr'                       # 超过 2% 的字符不在正常中英文/常用标点范围内
    chinese = len(re.findall(r'[\u4e00-\u9fff]', compact))
    latin = len(re.findall(r'[a-zA-Z0-9]', compact))
    return 'text' if chinese >= 10 or latin/len(compact) > 0.85 else 'ocr'
```

用正则做"正常字符配额"检查，判断 PDF 自带的文字层可不可信。注释很诚实：**这只是启发式，不能保证没有漏字或图文混排**。

### 两种模式

- `inspect`：遍历每页只报"页号 + 字符数 + 路由"，不输出正文——预检用，开销小。
- `read`：逐页提取文字 + `page.render(scale).to_pil().save(...)` 渲染 PNG 预览图。**文字页也渲染**，因为增强阶段需要拿页面图来裁剪。渲染比例来自配置（默认 2 倍），它参与阅读版本指纹。
- 每页处理都包在 `try/except` 里：单页失败输出 `{'page_number': n, 'error_code': 'pdf_page_failed'}` 继续下一页，**一页坏不影响整卷**。

## 三、`workers/ocr_worker.py`（63 行）—— PaddleOCR 小工

### 先查弹药再开工

```python
names = ['PP-OCRv5_mobile_det','PP-OCRv5_server_rec','PP-LCNet_x1_0_doc_ori','PP-LCNet_x1_0_textline_ori']
if any(not (models/name/'inference.pdiparams').is_file() for name in names):
    for page in config['pages']:
        emit({'page_number': page['page_number'], 'error_code': 'ocr_models_missing'})
    return 0
```

4 个模型各司其职：检测（文字在哪）、识别（文字是什么）、文档方向（图片是不是倒的）、文本行方向（行是不是横的）。缺任何一个权重文件：**逐页返回错误码，绝不自动联网下载**——"本地执行"是产品承诺。

### 日志驯服

```python
with redirect_stdout(sys.stderr):
    from paddleocr import PaddleOCR
    ocr = PaddleOCR(...)
```

Paddle 内部爱用 `print` 打日志。但本进程的 stdout 是**数据协议通道**，混进一行日志主进程的 `json.loads` 就炸。`redirect_stdout(sys.stderr)` 把 Paddle 的话全部改道到 stderr（→ 日志文件）。这个手法在两处用到（加载模型时、逐页预测时）。

### 逐页预测与一个重要细节

```python
results = list(ocr.predict(page['image_path']))
result = results[0]
processed = result.get('doc_preprocessor_res', {}).get('output_img')
if processed is not None:
    Image.fromarray(processed[:,:,::-1]).save(page['image_path'])
emit({'page_number': ..., 'payload': output, 'image_path': page['image_path']})
```

细节：如果 OCR 做了**方向校正**（比如页面本来是横躺的），识别框坐标是相对"转正后"的图片的。所以把转正后的图**存回原 image_path**，供后续视觉增强裁剪用——否则拿原始躺倒图按坐标裁剪会裁错地方。`[:,:,::-1]` 是把 BGR 转 RGB（OpenCV 和 PIL 的通道顺序相反）。

## 本篇小结

- `reading.py`：版本=管线名+模型逐字节指纹；worker 协议（清单入、JSONL 出、看门狗、finally 清理）；先落库再暂停；失败粒度是页。
- `pdf_worker.py`：启发式判断文字层可信度；每页独立容错；文字页也渲染预览图。
- `ocr_worker.py`：四模型协作；缺权重不联网；Paddle 日志改道 stderr；方向校正图回存保证坐标一致。
