# 07 · 调度队列：`pipeline.py`（237 行）

全项目的"总调度室"。两个类各司其职：
- `ProcessingPipeline`：**干活的**——把 阅读→增强→索引 三步串起来。
- `JobManager`：**管人的**——排队、派活、暂停、恢复、中断恢复。

先看简单的，再看复杂度爆炸但设计精美的 JobManager。

---

## 一、`ProcessingPipeline`（第 22–41 行）

```python
class ProcessingPipeline:
    def __init__(self, settings=None, reader=None, automatic=None, evidence=None):
        self.settings = settings or Settings.from_env()
        self.reader = reader or Reader(self.settings)
        self.automatic = automatic or AutomaticProcessor(self.settings)
        self.evidence = evidence or EvidenceService(self.settings)

    def run(self, project_id, document_id, pages, checkpoint=None):
        kwargs = {'checkpoint': checkpoint} if checkpoint else {}
        if checkpoint: checkpoint('reading', pages[0])
        reading = self.reader.read(project_id, document_id, pages, **kwargs)
        if checkpoint: checkpoint('vision', pages[0])
        automatic = self.automatic.process(project_id, document_id, pages, **kwargs)
        if checkpoint: checkpoint('embedding', pages[0])
        index = self.evidence.index(project_id, document_id, pages, **kwargs)
        return dict(reading=reading, automatic=automatic, index=index)
```

- 构造函数支持**依赖注入**：测试时可以传一个假的 reader（不真跑 OCR），但用真数据库——注释写明"测试因此能只替换昂贵推理，保留真实数据库"。
- `run()` 的顺序**不能变**：基础文字 → 机器有效文字 → 用这个版本的文字建向量索引。后面依赖前面的产物。
- `checkpoint` 是贯穿三层回传的回调——pipeline 自己在每阶段开头也敲一次，让 UI 能显示"当前在第几阶段的第几页"。
- 注意：`run()` 本身不知道"队列"的存在。CLI 的 `process-pages` 直接调它，网页才走 JobManager——**干活和调度彻底解耦**。

## 二、`JobManager` —— 数据库-backed 的可恢复队列

### 1. 开篇的三锁声明（务必先读懂这段，第 54–58 行注释）

```python
# 三类锁不要混淆：
# 1. _mutex：仅防止本进程重复启动后台线程。
# 2. PostgreSQL 74332103：跨应用进程的队列执行权，贯穿 drain()。
# 3. PostgreSQL 74332104：短事务内串行化入队／暂停／继续操作。
# 模型内存竞争另由 retrieval.model_slot() 的文件锁控制。
```

| 锁 | 类型 | 保护什么 | 持有多久 |
| --- | --- | --- | --- |
| `_mutex` | Python 线程锁 | 本进程不重复起后台线程 | 瞬时 |
| `74332103` | pg 会话级 advisory lock | **全机只有一个执行者** | 整个 drain() 期间（跟连接走） |
| `74332104` | pg 事务级 advisory lock | 控制操作不交错 | 单个短事务 |

为什么 74332103 选**会话级**锁？——它绑定数据库连接，`commit()` 不会释放，**连接断开（进程崩溃/被杀）数据库自动释放**。这就是"多应用进程共享一个队列"和"崩溃后锁必然归还"的全部秘密。

### 2. `enqueue()` —— 排队

- **暂停中的任务也算"活动任务"**——注释点破：不能通过再点一次"自动处理"绕开暂停状态。想继续必须走 resume。
- 数据库还有一道兜底：部分唯一索引 `processing_job_active`（只对活动状态建唯一索引），并发下也不会插出两个活动任务。
- `wake()` 只是"叫醒"后台线程，不阻塞请求——所以接口能立刻返回 202。

### 3. `latest()` 与中断的派生判断

```python
row['worker_present'] = not self._lease_available(conn)      # 探测执行锁
```

精妙之处：**数据库状态和"实际有没有人在跑"是两回事**。任务状态写着 running，但执行锁没人持有 = 执行者死了 = 中断。`_lease_available` 用 `pg_try_advisory_xact_lock` **试探**拿锁——拿得到说明没人持有（探测锁随本次查询事务结束自动释放，不会真的抢走）。注释强调：**GET 请求只报告中断，不修复**——修复交给启动时或控制操作，只读请求不该有副作用。

### 4. `_recover_orphans()` —— 中断任务的收束

```python
@staticmethod
def _recover_orphans(conn, document_id=None):
    # 只有拿到执行权，才能确认旧执行者已不再持有队列锁。
    # 不直接重跑旧 running：保留成果并暂停，用户明确继续后复用原任务。
    query = '''UPDATE dd_agent.processing_jobs SET status='paused',
        progress=jsonb_set(progress,'{recovery}',jsonb_build_object(
            'reason','worker_lost','previous_status',status,'recovered_at',clock_timestamp())),
        updated_at=clock_timestamp() WHERE status IN ('running','pause_requested')'''
```

- **前提是已持有 74332103**——否则你怎么知道旧执行者真的死了？（它可能只是更新慢。）注释一句话点破因果关系："只有拿到执行权，才能确认旧执行者已不再持有队列锁"，以及 **"Never infer abandonment from age"**（绝不靠"多久没更新"猜任务死了——慢任务会被误杀）。
- 处置方式：**转为 paused 而不是重跑**。带上 recovery 元数据（原因、原状态、时间）。用户点"继续"才恢复——这就是 README 说的"不会因重启默默重跑"。

### 5. `_save()` —— 防状态覆盖的 CASE 魔法

```python
def _save(self, job, status, progress, error=''):
    # 推理期间用户可能刚请求暂停。不能用旧线程的 running 进度覆盖新暂停状态。
    conn.execute('''UPDATE dd_agent.processing_jobs SET status=CASE
        WHEN status='paused' THEN 'paused'
        WHEN status='pause_requested' AND %s NOT IN ('paused','failed') THEN 'pause_requested'
        ELSE %s END, progress=%s, error_code=%s, ... WHERE id=%s''', ...)
```

场景：worker 正在跑一页（要花几分钟），这期间用户点了暂停（状态变 pause_requested）。worker 跑完想保存进度——**如果直接把状态写成 running，暂停请求就被冲掉了**。CASE 表达式在 SQL 层原子地保护状态：已经是 paused 的不能被改回；有暂停请求在挂着就保持挂起。**但进度照存**——刚完成页的信息不丢。

### 6. `_checkpoint()` —— 暂停的触点

```python
def _checkpoint(self, job, progress, stage, number):
    with self.database.connect() as conn:
        row = conn.execute('SELECT status FROM dd_agent.processing_jobs WHERE id=%s FOR UPDATE', ...).fetchone()
        if row['status'] in ('pause_requested','paused'): raise ProcessingPaused()
        if self._stop.is_set(): raise ProcessingStopped()
        progress.update(stage=stage, current_page=number)
        conn.execute('UPDATE dd_agent.processing_jobs SET progress=%s, ... WHERE id=%s', ...)
```

处理链路每隔一小步就敲一次这个检查点：FOR UPDATE 锁行查状态 → 用户请求了暂停就抛 `ProcessingPaused`（ control.py 那两个异常在这里登场）→ 服务要停就抛 `ProcessingStopped` → 没事就更新进度。**current_page 是"当前检查位置"不是"完成数"**——恢复时会回到较早的页重检，界面上看到页码"倒退"是正常的。

### 7. `drain()` —— 心脏，逐段读

```python
def drain(self):
    with self.database.connect() as lease:
        if not lease.execute('SELECT pg_try_advisory_lock(74332103) AS acquired').fetchone()['acquired']:
            return                                    # 别的进程在干活，我走
        try:
            self._recover_orphans(lease)              # 拿到锁了，收束孤儿
            lease.commit()
            while not self._stop.is_set():
                job = lease.execute("SELECT * FROM dd_agent.processing_jobs
                    WHERE status IN ('queued','running','pause_requested') ORDER BY created_at,id LIMIT 1").fetchone()
                lease.commit()
                if job is None: return                # 队列空了
```

- `pg_try_advisory_lock`（非 try xact）：**会话级**，跟随 `lease` 这个连接——整个 drain 期间锁都在。
- 拿到锁第一件事：收束孤儿任务。
- 循环取最老的待处理任务（FIFO）。

```python
# 不能只从 processed_pages+1 开始，否则暂停期间变更的旧页会漏重建。

```

**为什么每次都从第 1 页开始而不是接着上次的进度？** 暂停期间可能发生：源文件换了、OCR 权重换了、模型换了。如果从"上次停的地方"继续，**变更的旧页就永远漏掉了**。所以全量重检，靠各层的版本化机制自动跳过没变的页（已索引页 skip、同版本成功页 skip、候选缓存命中 skip）——**没变的页几乎零成本，变了的页自动重建**。这就是"进度"和"重检"能同时成立的原因。

四个出口：
- **正常完成**：有失败页 → partial，全成 → completed。之后还有一次"补刀" UPDATE：如果最终保存的瞬间用户恰好点了暂停，状态改成 paused（竞态收尾）。
- **用户暂停**：存 paused，进度完整保留。
- **服务停止**：存 paused + recovery 标记，直接 return——**重启后不默默重跑**。
- **其他异常**：failed，error_code 只写 `local_processing_failed`——**不落原始异常文本**，防止凭据/客户文件名泄露进数据库。
- finally 里显式解锁（连接关了数据库也会自动释放，双保险）。

### 8. `wake()` / `_work()` / `close()` —— 线程管理

```python
def wake(self):
    with self._mutex:
        if self._thread and self._thread.is_alive(): return   # 已有线程在跑就不重复起
        self._stop.clear()
        self._thread = Thread(target=self._work, daemon=True, name='local-document-processor')
        self._thread.start()

def _work(self):
    while not self._stop.is_set():
        try: self.drain()
        except (psycopg.Error, OSError): pass     # 数据库闪断等：吞掉，下轮再试
        self._stop.wait(3)                        # 每 3 秒醒一次
```

- 后台线程是**轮询模型**：每 3 秒尝试 drain 一次。try 拿不到锁就空转——注释说这同时解决"另一个进程释放锁后我能接上"的问题。
- `daemon=True`：主进程退出时线程不阻止退出（配合 drain 里的 ProcessingStopped 逻辑安全收尾）。
- `close()`：`_stop.set()` + `join(timeout=1)`——**协作式停止**，只等 1 秒不强杀（正在进行的模型计算不受影响，安全点保存后自然停下）。

## 本篇小结

- 干活（Pipeline）与调度（JobManager）解耦：CLI 直调前者，网页走后者。
- 三锁体系：线程锁 / 队列执行租约（会话级，断连自动释放）/ 控制串行化。
- 中断恢复的哲学：**靠锁判断死活（不看时间戳），转为暂停不自动重跑，恢复时全量重检 + 版本化跳过**。
- `_save()` 的 SQL CASE 防止旧线程覆盖新暂停；checkpoint 是暂停信号的传播触点。
