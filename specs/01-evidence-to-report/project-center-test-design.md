## 1. 怎么写断言

每条测试使用合成字节或页面夹具，不读取客户材料、业务库或模型目录。断言看状态码、错误码、项目标识、材料标识、定位种类和正文是否出现。不断言私有得分阈值已经等于业务正确。

新增行为先写会失败的测试。失败必须是业务结果与规格不符，例如非 PDF 仍返回“暂不支持”、无当前项目时检索请求仍被发出、缺口接口不存在因而得到 404。不把 `ModuleNotFoundError`、缺数据库夹具或导入错误当成红灯。

已经正确的隔离行为，补测试是回归。这些测试在当前代码上应当通过。不把它们写成故意失败，也不把“补上了测试”说成先红后绿。若回归测试失败，按缺陷修到绿，并说明原先哪条路径漏测。

通过之后只做让测试仍绿的整理，再跑仓库既有全量工程回归。全量回归的数字写回 tasks.md 时必须带运行标识；本设计不预写数字。

模型、GPU 和整卷不进入上述工程循环。mock 的嵌入和重排只能证明过滤、版本和项目边界，不能证明 OCR 或检索质量。

## 2. 分层

| 层 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| L0 纯函数 | 文件名清理、定位对象、公式格是否有缓存值 | 页面流程和数据库隔离 |
| L1 服务与 HTTP | 项目条件、登记、检索各支、补读、MCP | 浏览器是否选错项目 |
| L2 前端脚本或浏览器 | 当前项目、空／加载／失败／部分／完成、旧响应 | 向量是否语义正确 |
| L3 真实模型 | 小批量 OCR、嵌入和重排与来源一致 | 客户整卷或法律结论 |
| L4 整卷与固定集 | RG-04、RG-05f 的资源和质量记录 | 由 L1 的 mock 代替 |

L0–L2 是工程完成信号。L3／L4 是单独的验收信号。工程完成和模型／整卷验收写在 tasks.md 同一行的状态与验收格里，不另开第二张表，也不把只有工程结果的行标成整卷已完成。

## 4. 失败应当长什么样

先红的测试在实现前应当失败在断言或约定的 HTTP 状态上。例如：

- 检索页在无项目时发起了 `/api/projects/` 下的搜索，或选中了某个项目。
- 上传合成 DOCX 得到的状态不是规格在该阶段要求的状态。未确认格式前，要求是“暂不支持”；确认后，要求是抽出夹具句子。改预期的那一次才允许从绿改成红。
- 缺口清单路由返回 404，测试断言的是“当前项目看不到失败页清单”，并同时断言响应不含其他项目正文。

不接受的红灯：收集依赖失败、测试文件无法导入、数据库未建表、故意调用不存在的 Python 名字。缺路由若是被测行为的一部分，断言写在 HTTP 客户端的状态和正文上，不写在 `import` 上。

## 5. 确认后的实施顺序

这里的顺序是将来写代码时的 red → 最小 green → refactor → 全量工程回归。本轮停在设计。

1. 只添加 TD-C 和 TD-A05、TD-A07 这类回归。预期直接绿。整理夹具，跑全量工程回归。
2. 添加 TD-A01–A03、A06。看到业务失败后，只改当前项目的传递和空状态，直到这些断言变绿。再跑全量回归。
3. 添加 TD-D01–D04。按红灯最小补 PDF 范围的缺口、补读和过滤。不在这一步解析 Office。全量回归。
4. 用户确认格式之前，TD-B01 保持“暂不支持”的绿。确认某一格式后，只把该格式的 TD-B 预期改掉，看到红灯，再做该格式的最小解析和定位。一种格式一轮。全量回归。
5. TD-D05 只做清单与夹具完整性。真实模型和整卷另开运行，不和 1–4 的工程绿灯混写。

任何一步发现回归测试由绿变红，先恢复原有项目边界，再继续新行为。
