## 1. 目标与已确认前提

用户导入原始文档、指定尽调范围和报告模板，Agent 完成材料阅读、事实提取、交叉核对、问题识别、法律分析和报告起草。系统应支持并购、不良资产、IPO 等多种尽调，逐步增加专项能力。

- 输入是图片、PDF、Word、Excel、PPT 等原始材料，单项目可能达到数 GB 或更大。
- 不要求用户预先提供结构化数据。材料目录、事实记录、证据引用、问题清单和处理状态由系统自动建立。
- 报告模板可变，核心审查事项具有复用性；报告可能超过百页。
- 材料与 RAG 保存在本地，OCR／视觉复核／检索优先本地运行；用户明确报告生成会调用外网模型，服务商和具体发送范围在接入时配置。
- 向量化与重排序采用下载好的开源模型，本地运行不要求 Docker 或 WSL；数据库是否使用容器单独决定。原生 Windows 作为首轮环境验证路线，具体依赖组合需实测。
- skill 保存审查方法和写作规则；项目事实与进度由持久化记录管理，可自动生成摘要供模型使用。
- 整体规格与 P1 阶段规格已形成；按 A/B/C 分段实现和验收。

## 2. SDD 工作方式

每个功能包按以下顺序推进：

`明确业务规格 spec.md → 明确实现方案 plan.md → 拆分 tasks.md → 实现与验证 → 更新规格及验收记录`

- 规格定义用户故事、范围、成功标准、异常状态和非功能要求；方案说明如何实现。
- 每条需求、验收条件和任务分别编号，建立“需求 → 任务 → 测试或人工验收 → 结果”的对应关系。
- 每个功能包保持可独立评审，避免先写一份过大的规格，再一次性实现全部能力。
- 影响业务范围的未决问题在相关阶段开始前确认；普通实现细节由开发阶段解决并记录。
- 发现假设不成立，先修正规格和受影响验收条件，再继续实现；不以代码现状倒推需求。
- 每个功能包完成后保存可演示结果和验证记录；未覆盖项必须明确列出。

## 3. 首版范围建议

首版目标是验证“能否从原始文档形成有依据、可核查的报告”，不同时完成所有尽调类型。

首条纵向链路已依据用户样例调整为“公司基本情况与历史沿革”：工商扫描档案作为原件，DOCX 报告作为章节参考。重大合同留到后续专项。

首版应具备：导入材料、显示处理情况、自动提取事实、定位原文、标记矛盾与缺失、生成章节、查看和修改结果、导出 Word。法律分析先限定在获准的法域、审查事项及经确认的法源范围内。

首版暂不包括：训练专用大模型、自动对外提交报告、完整覆盖所有专项审查、复杂多人审批和商业多租户体系。正式交付前的专业复核由业务方明确，不把模型检查标为人工认可。

## 4. 总体实现方案

```text
本地原件 → 已有 PDF／OCR／视觉工作进程 → 带来源文字 → 本地向量库及重排序
                                                     ↑
现有材料工作区／首轮复用 Harness 交互入口 → DeepSeek Harness＋外网生成模型
                                                     ↓ MCP 工具
                            项目覆盖、检索、证据补读、工作文件、Word 操作
                                                     ↓
                         项目独立工作目录、章节／引用版本、可编辑 Word 草稿
```

大模型按 skill 决定读哪些材料、整理哪些事实、怎样组织章节、何时补证和修订；工具执行具体操作并返回真实结果。模型引用原文进行内容核对，工具检查标识、项目归属、版本和定位是否有效。Word 工具根据模型提供的内容实际创建、编辑和保存文档，不由配置文件自行生成报告。

材料后台队列与 Harness 会话分开：已有 OCR／向量任务继续由本地服务运行，报告会话恢复不能被当成后台工作进程恢复。项目笔记、章节和引用清单落盘，聊天压缩摘要不是唯一恢复依据。先用单 Agent 完成两章，复用现成交互、会话与文档能力，再评估专用 UI。

### 候选技术基线

以下用于首轮验证，具体版本在对应功能包中核验、锁定并记录许可证；不以此表代替样本评测。

| 部分 | 候选基线 | 选型原则 |
| --- | --- | --- |
| 本地应用 | Python、FastAPI；本地浏览器界面 | 本地服务默认仅监听本机，部署到局域网前补齐身份和权限规格 |
| 原始文件 | 本地文件存储，保留对象存储适配接口 | 原件不可被解析或生成流程覆盖 |
| 业务数据与工作文件 | PostgreSQL 保存既有材料／索引／任务；项目独立目录保存报告工作文件 | 首轮只补会话／运行与文件关联等必要元数据；事实笔记、时间线和问题由模型生成，不先建完整事实表体系 |
| 检索 | pgvector＋中文词法检索及精确字段索引 | 检索效果不达标时再评估独立搜索服务，不预先叠加多套数据库 |
| 文档处理 | Docling、PaddleOCR、格式原生解析库 | 按文件特征分流，通过真实样本确定组合 |
| 向量与重排序 | 本地 Qwen 预训练检索模型作为评测基线 | 无需训练或强制容器化；从 CPU 小批次验证，再测试已有显卡兼容性 |
| 报告模型与 Agent | DeepSeek Harness profile、模型适配和 skill；必要时用其 Python SDK 驱动独立运行时 | 固定通过验证的版本；直接复用工具循环与会话，生成服务商和范围按项目配置 |
| 材料后台任务／工具桥接 | 现有本地持久队列＋Python MCP 服务 | 材料处理保留；报告运行交给 Harness，不增加第二套自研报告引擎；现有 API 不是 MCP 端点，需要薄适配 |
| Word 操作 | 先验证可复用 Word／Office 工具；缺口用 python-docx／docxtpl 等薄封装 | 模型负责内容和结构，工具负责编辑／导出；固定占位符只作可选模板方式，Office 转换不等于报告起草 |

报告框架方向采用 Harness，具体版本、profile、入口和 Word 工具在接入任务中验证；模型型号、硬件优化与新增队列组件按样本和环境决定。

### 最小持久化约定

- 复用现有项目、原件、页码／内容版本、机器结果、索引和材料任务表。
- Harness 保存会话；项目目录保存提纲、事实／时间线笔记、覆盖说明、引用清单、章节草稿、Word 和修订历史。笔记格式按实际需要选择 Markdown／轻量 JSON，不要求完整实体模型。
- 最小运行清单关联 project、report run、session、模板／skill／模型版本及输出文件；必要时新增少量元数据，不新建完整事实服务。
- 引用清单只保存工具返回的真实来源标识、版本与定位；它保证可回查，不证明内容正确。模型借助原文核对支持关系，未解决项随稿输出。
- 用户提供的参考报告只用于章节、写法和模板；内容事实仍回到原始证据，未提供材料的部分保留未知。

## 5. 分阶段路线与验收门槛

| 阶段 | 开发内容与交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 范围与工程样本 | 原件为工商扫描／混合 PDF，报告作参考，基本情况与历史沿革为首轮章节 | 已确认调整范围并收到样例；法律部分后移 |
| P1-A 基础工程 | 本地页面、配置检查、数据库迁移、项目、材料登记与去重 | 原件保存、同名不同内容保留、记录重启可读；未配置数据库时明确提示 |
| P1-B 本地阅读检索 | PDF／原生 Word 试点分流、OCR 质量改进、重要页视觉复核及受控并行、证据定位、切片与检索 | 按 B-Q／B-R／B-P 评测选择策略；处理成功与质量区分；查询可回到项目原件；资料识别不默认外发 |
| P1-C 工具接入及后续报告 | 当前先在 RAG 限定验收后接入已有桌面 Harness 的 MCP；Word／尽调 skill／两章报告暂缓 | RAG 工具遍历、覆盖、补读和项目隔离先验证；恢复报告阶段后再验收两章 Word 及真实生成 |
| P2 多格式与批量处理 | 扩展图片、复杂 Word、Excel、PPT 等格式及完整批量队列、分类、断点恢复与局部重试 | 每个输入均有处理结果；加密、损坏、不支持和低质量文件单独列出；重复导入不重复生成事实；失败不阻塞其他文件 |
| P3 事实核对与检索 | 扩充模型方法包、补读／清单遍历和计算工具；按需增强主体／时间核对与混合检索，不强制独立事实引擎 | 精确编号和语义条款均可查找；抽取和证据支持达到 P0 阈值；“未检索到”不被自动解释为“不存在” |
| P4 审查与法律分析 | 版本化审查方法包、材料要求、问题记录、受控法源库及逐问题分析 | 每条法律结论列明事实、法源版本、适用理由和未决条件；法域或关键材料不足时输出待核实项；通过专业评测 |
| P5 模板与长报告 | 章节映射、业务内容与排版分离、跨章节校验、百页规模导出、追加材料和修改后的增量更新 | 同一事实可输出到不同模板；新增材料能标记受影响结论和章节过期；保留人工修改并展示更新差异；长报告渲染检查通过 |
| P6 专项与部署扩展 | 逐个增加并购、不良资产、IPO 专项规格；比较云端 API 与内网模型；完整备份恢复和容量压测 | 每个专项独立通过标注样本验收；不良资产按逐笔台账验证；部署满足数据边界、处理质量与吞吐要求 |

各阶段验收对应范围，不要求完成全卷、全格式或全部 B-Q／B-P 才接入 MCP；当前先完成 RG 限定样本验收，报告试点暂缓。恢复报告阶段后仍可使用限定样本和明确覆盖。

P1 先证明端到端路径，P2–P4 逐步提高材料覆盖和分析能力，P5 再系统验证复杂模板和长报告。全离线模型部署可以延后，但模型可替换与禁止外发的控制在 P1 建立。

## 6. 必须提前写入各阶段规格的行为

- **处理中：** 展示文件总量、已完成、失败、待复核和当前阶段；进度可以恢复，不展示无依据的完成时间。
- **无材料：** 提供导入入口；只有模板时显示所需材料，不能直接填造事实。
- **部分完成：** 允许查看已完成内容，明确未处理范围；不能将部分材料生成的报告标为完整完成。
- **失败或断网：** 原文件保留，可重试失败步骤；外部模型不可用时，本地解析和检索继续运行，生成任务明确等待或失败。
- **缺失和冲突：** 保留未知值、不同来源及其时点；日期不同不直接判为冲突，上传较晚也不自动认定为有效版本。
- **增量变化：** 文件、事实或法源更新后，追踪依赖并标记旧分析和章节过期；不静默覆盖人工修改。
- **文档特例：** Excel 公式与缓存值分开处理，缺少可靠结果时标记；Word 页码不稳定时使用段落标识，渲染页码关联到指定渲染版本。
- **可访问性：** 导入、查看证据、修订和导出支持键盘操作；状态和错误不只依赖颜色表达。

## 7. 数据边界与工程约束

- 原始文件、解析文本、事实库、索引和报告默认保存于本地；API 和 SDK 使用同一数据发送策略。
- 外部模型权限尚未确定，默认不外发。P0 明确允许的服务及材料范围后，相关项目才能使用云端模式。
- 明确提示首次批量抽取也可能发送大量文本；不以“仅发送片段”描述为完全离线，摘要和向量也不默认视为脱敏。
- 每次模型调用记录模型、规则和输入版本、发送范围、耗时及费用信息；默认日志不复制原文和密钥。
- 文件内容属于待处理数据，不能改变系统规则或调用权限；文件转换不执行宏，使用受限运行环境。
- 各项目检索与数据访问均带工作区边界。局域网或多人版本单独补充鉴权和访问控制规格。
- 重试、重复导入和断点恢复不得重复写入同一结果；云端超时后的重复计费风险需在调用记录中可见。
- 保存解析器、抽取规则、模型、模板和法源版本；升级须运行固定回归集，并能识别需要重新处理的数据。

## 8. 验证与质量度量

质量阈值按阶段依据代表性样本制定，在保留集评测前冻结。当前 OCR 试验采用 P1 规格 B-Q 的暂定门槛，不宣称系统已经达到目标，也不在看到保留集结果后随意放宽阈值。同卷页级策略试验不能替代独立文件／项目的产品级验收。

| 维度 | 如何验证 |
| --- | --- |
| 材料覆盖 | 输入文件逐一对应处理结果；失败和排除原因可见，不能静默遗漏 |
| 事实抽取 | 按字段测准确率和召回率；金额、主体、日期、单位单独统计，未知值不能用猜测填充 |
| 证据支持 | 检查引用能否定位，以及原文是否真正支持该陈述；不能只检查链接存在 |
| 检索效果 | 使用有标准相关证据的查询测召回；分别覆盖名称编号、同义条款、跨页表格 |
| 风险分析 | 专业人员标注关键问题、反例和材料不足情形，统计遗漏与无依据判断；不只让模型评价模型 |
| 报告质量 | 核对章节间主体、金额、时间和结论一致性；Word 渲染后检查目录、编号、分页及表格 |
| 更新可靠性 | 补充协议、证据纠正和法源变化后，只重算受影响内容，同时保留人工修订 |
| 成本与性能 | 记录每千页解析时间、模型调用量、单项目成本、增量耗时及高峰资源使用；报告硬件与样本组成 |

测试按风险安排：字段归一化、计算、权限边界、幂等与状态迁移做自动化测试；模型抽取和分析用固定评测集；端到端用代表性材料；排版做渲染检查。不为简单可逆文本修改添加无价值测试。

生成结果中的引用必须能解析到真实记录；未解决的关键缺失、冲突或处理失败必须在结果中可见。满足这些工程条件仍不等于法律结论已获得专业认可。
