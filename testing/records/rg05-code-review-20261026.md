## 发现

1. **[P1] 内容单独变化时，旧正文缓存不会失效。** `src/dd_agent/static/reader.js:242–245` 在 status_revision 不变、content_revision 改变时只更新全局修订，再调用 showPage。目录条目的 source_revision 未更新，showPage:149 仍判定缓存有效，extras 也按旧修订命中。典型触发是基础页状态仍成功而机器增强生成新文字；页面确认了新全局修订，显示却持续为旧内容，普通刷新按钮也不强制失效。复现：新内容探测后正文请求 0 次，显示 OLD，全局修订已经是 new-content。修复应按选中页核对新来源，失效对应正文／增强缓存；只有其他页改变时仍应避免重复下载当前页。

2. **[P2] 基础识别面板展示有效增强文字。** `reader.js:115` 只请求 view=effective，renderPage:93–94 把同一 data.text 填入当前文字和“基础识别文字与行信息”。存在增强时，两区都显示增强结果，用户看不到真正基础 OCR，还可能把基础行框与增强文字误认为对应关系。复现两区同为 ENHANCED，只有一条 effective 请求。应独立使用 raw 视图，详情展开时再按需加载原始文字／行框，分别绑定对应修订。

3. **[P2] 切到未处理／读取失败的页仍保留上一页原图。** `reader.js:129–135` 只在 not_processed 时清正文，不清图片和旧页状态；showPage 开始也不清理原图。复现选中第 2 页后仍显示 `/page-one?rev=s`，页状态仍是第 1 页；其他网络错误还可留下上一页正文。这会把错误来源展示给当前页。应为切页设置明确的加载／失败状态，清理旧页图文与标题，同时保留请求代次保护。

4. **[P2] 新阅读器仍自动拉全历史。** `reader.js:162–165` 每次加载增强信息都调用旧 automatic／review 接口；AutomaticProcessor.state 和 ReviewService.state 无 LIMIT，返回整段机器历史、人工历史和候选输出。新增的 `/history` 分页接口完全没有被阅读器调用，详情未展开也会下载这些数据，extras Map 还会按访问页保留整份结果。隔离库用 30 条每条 20,000 字的机器历史复现：automatic 响应 **1,869,441 字节**；分页历史默认 10 条预览仅 **17,673 字节**。应分离当前结果与历史，历史展开后分页请求，并限制前端缓存规模；不要求削减当前页的有效正文。

5. **[P2] 同一基础页的多个增强记录被同时标为当前版本。** `src/dd_agent/page_queries.py:177–178` 用 base_revision 是否相等判断 is_current，但一份基础 OCR 可产生多个增强策略／重试记录；effective_document_pages 实际只选最新一条。隔离库写入同一 raw_revision 下 3 个增强记录，历史接口把全部 3 条 is_current 标为 true。应与有效视图选择的实际机器记录 ID／来源修订一致；“基于当前基础页”应另设字段，不能等同“当前生效”。还需覆盖当前记录位于其他分页窗口的情况。

6. **[P2] 单计时器没有保证轮询请求串行。** `reader.js:216–220` 只有 polling 开关，没有 in-flight guard；可见性变化、刷新按钮和暂停／继续完成时都能直接调用 poll，已有 poll 尚在等待时会重入。clearTimeout 只能清下一次定时器，不能取消正在执行的请求。复现同一时刻两个 processing 请求并行；迟到响应可回写旧任务状态和目录，额外增加数据库压力。应把同时到达的触发合并为一条在途刷新，必要时完成后追加一次，并对目录响应增加代次／修订保护。该项是请求可重入缺陷，不声称每次都会产生双倍轮询频率。
